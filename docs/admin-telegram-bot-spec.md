# Техническое задание: отдельный Telegram-бот администратора

**Статус:** проект ТЗ; перед реализацией требуется устранить блокер по схеме Supabase.  
**Объём текущей работы:** только документ. Код, конфигурация и база данных не изменялись.  
**Дата проверки кода и API-схемы:** 2 октября 2026 г.

## 1. Цель

Создать отдельного Telegram-бота для ограниченного круга администраторов. Бот должен показывать сводную статистику пользователей, сведения о привязанных EVM-кошельках и разрешениях, баланс пользователя, историю списаний и запускать только разрешённые операции списания USDT.

Автоматическое списание должно работать только для **USDT в кошельке пользователя в Ethereum Mainnet**, через существующую схему Permit2, после отдельного, понятного пользователю согласия. Это не списание внутреннего USDT-баланса сервиса.

## 2. Зафиксированные продуктовые решения

- Админ-команды размещаются в **отдельном Telegram-боте**, не в публичном боте Mini App.
- Автосписание запускается после каждого нового подтверждённого поступления USDT на разрешённый кошелёк.
- Если текущий on-chain баланс кошелька достиг **10 USDT**, списывается **98% текущего баланса**, а не только сумма последнего поступления.
- Для расчёта используется точное значение USDT в base units; порог 10 USDT равен `10,000,000` base units при 6 decimals. Курс USD не запрашивается.
- Отдельного фиксированного максимума суммы автосписания в USDT не задано: для каждого подходящего события расчётный максимум — 98% фактического текущего баланса кошелька. Дневные и глобальные аварийные ограничения — отдельные предохранители; их значения пока не заданы, и при срабатывании они блокируют транзакцию целиком, а не уменьшают её сумму.
- Каждое списание требует отдельного согласия пользователя именно на автоматическое списание 98%. Обычное on-chain разрешение Permit2 само по себе таким согласием не считается.
- Автосписание из уже имевшегося на кошельке баланса при первом включении **по умолчанию не выполняется**. Первичный баланс можно списать только после отдельного действия/подтверждения пользователя. После включения отслеживаются новые поступления.
- Целевой адрес задаётся серверной конфигурацией и должен входить в действующий allowlist. Администратор не вводит произвольный адрес назначения в чат.

## 3. Термины и границы баланса

1. **Зарегистрированный пользователь** — запись в `internal_ton_users`, созданная после успешной Telegram-аутентификации Mini App.
2. **Запись об EVM-разрешении** — сохранённая связь Telegram ID и Ethereum-адреса в БД. Её статус не доказывает, что разрешение всё ещё действительно в блокчейне.
3. **Действующее on-chain разрешение** — свежая проверка Ethereum Mainnet подтверждает необходимый USDT allowance к Permit2, действующий Permit2 allowance оператору, достаточный лимит и неистёкший срок.
4. **Согласие на автосписание** — самостоятельное, отзывное согласие пользователя с политикой автосписания 98%. Это отдельная запись и отдельный пользовательский шаг, не эквивалент подписи/approval транзакций.
5. **USDT в кошельке** — on-chain баланс токена USDT Ethereum Mainnet, читаемый у контракта токена. Только этот баланс может использоваться в `Permit2.transferFrom`.
6. **Внутренний USDT** — баланс сервиса из `internal_usdt_balances`; он не находится в кошельке и не может быть списан через Permit2 или `transferFrom`. Бот может показывать его только отдельным полем с явной меткой «внутренний баланс».

Поддержка других сетей, токенов и внутренних балансов в автосписании не входит в первый релиз.

## 4. Пользовательские и административные интерфейсы

### 4.1 Админ-бот

Админ-бот работает только в личном чате с пользователем из `ADMIN_TELEGRAM_IDS`. В группах и каналах команды, данные пользователей и финансовые действия запрещены.

Предлагаемый набор функций:

| Функция | Результат и ограничения |
|---|---|
| `/stats` | Количество зарегистрированных пользователей; пользователей с сохранённой EVM-связью; кошельков с активной записью разрешения; кошельков, недавно подтверждённых on-chain; число включённых автосогласий; число списаний за период. Метрики с разным смыслом показываются раздельно. |
| `/users` | Постраничный список пользователей. По умолчанию показывать Telegram ID, дату регистрации/последней активности и сводные статусы; не выводить лишние персональные данные. |
| `/user <telegram_id>` | Карточка пользователя, связанные EVM-адреса, статусы DB и последней on-chain проверки, автосогласие и последние списания. |
| `/approved` | Постраничный список EVM-кошельков с сохранёнными разрешениями. Отдельно маркировать «статус в БД» и «текущий on-chain статус»; не выдавать устаревшую запись за подтверждённое разрешение. |
| `/balance <telegram_id>` | On-chain USDT каждого связанного кошелька, Ethereum Mainnet, время/блок проверки; внутренние балансы — только отдельными строками и с явными подписями. |
| `/charges` | История ручных и автоматических операций с фильтром по пользователю, статусу и периоду; сумма, получатель, причина/триггер, tx hash и статус подтверждения. |
| `/charge-preview <telegram_id> <amount>` | Предпросмотр разового списания: сеть, актив, точная сумма, адрес пользователя, адрес назначения, комиссия/кто платит gas, ограничения и причина. Не отправляет транзакцию. |
| `Подтвердить списание` | Отправляет только показанную в предпросмотре операцию, после повторной проверки баланса, разрешения, адреса назначения и лимитов. Подтверждение одноразовое и ограничено по времени. |
| `/autodebit <telegram_id>` | Просмотр статуса отдельного согласия, порога, политики и последней проверки. Бот не может создать согласие за пользователя. |
| `/autodebit pause` | Глобальная аварийная остановка новых автоматических транзакций. Уже отправленные транзакции не отменяются. Возобновление требует отдельного подтверждения. |
| `/health` | Статус Supabase/API, RPC, отсканированный блок, задержка очереди, баланс gas оператора и состояние аварийного выключателя. Не раскрывает ключи и URL с секретами. |

Формат команд может быть заменён на кнопки и меню, но действия и проверки должны остаться теми же. Списки постраничные; адреса и идентификаторы в общих списках маскируются. Полное значение показывается только в карточке после запроса администратора.

### 4.2 Согласие пользователя

До включения автосписания пользователь должен увидеть и отдельно подтвердить:

- сеть и токен: Ethereum Mainnet USDT;
- что списывается 98% текущего баланса при выполнении триггера, а не 98% только последнего поступления;
- порог: текущий баланс не менее 10 USDT;
- триггер: новое подтверждённое входящее поступление;
- адрес назначения или его однозначный идентификатор;
- что при каждом таком событии может быть отдельная on-chain транзакция;
- как отключить автосписание и отозвать on-chain разрешение;
- что уже имеющееся разрешение Permit2 не является достаточным согласием на это правило.

Согласие включается только действием пользователя в Mini App либо равноценном подтверждённом пользовательском интерфейсе. Администратор не может включить автосписание за пользователя. Отказ, отзыв согласия или отзыв on-chain разрешения немедленно запрещают новые операции.

## 5. Поток автоматического списания

1. Пользователь связывает Ethereum-кошелёк с Telegram-аккаунтом по существующему challenge/signature flow. Адрес должен быть связан с одним Telegram-пользователем; чужой адрес нельзя привязать по одному публичному tx hash.
2. Пользователь отдельно включает автосписание для конкретного кошелька и принимает версию политики. Согласие сохраняется в БД с временем и идентификатором версии текста.
3. Сервис наблюдает Ethereum Mainnet `Transfer` events официального контракта USDT для кошельков с активным согласием. Сканер использует сохраняемый курсор и обрабатывает только подтверждённые/финализированные события.
4. После каждого нового подтверждённого входящего события сервис повторно читает текущий `balanceOf(owner)` и оба разрешения on-chain. Если баланс меньше 10 USDT, событие закрывается без списания; следующее новое поступление снова запускает проверку.
5. Если баланс не менее 10 USDT, сумма равна `floor(balance_base_units × 9800 / 10000)`. Расчёт выполняется целыми числами, без `float`. Транзакция не может превысить свежепрочитанный баланс, остаток целится примерно в 2%.
6. Перед отправкой сервис проверяет активное согласие, DB-связь пользователя и кошелька, chain ID, адрес токена, USDT allowance к Permit2, Permit2 allowance оператору, срок/nonce, allowlist получателя, лимиты и аварийные выключатели.
7. В БД резервируется списание с уникальным idempotency key, привязанным к событию. На один входящий log event допускается не более одной автоматической операции.
8. Операции одного кошелька выполняются последовательно. Новые события во время незавершённой транзакции сохраняются и обрабатываются безопасно после сверки предыдущей операции.
9. Успех фиксируется только после подтверждённой транзакции. Пользователю отправляется уведомление с суммой, сетью, адресом назначения в маскированном виде и ссылкой/tx hash; администратору доступна запись аудита.
10. При неизвестном результате отправки (тайм-аут после возможной отправки) операция переходит в состояние сверки. Повторно отправлять деньги с новым ключом до проверки nonce/receipt/tx нельзя.

### 5.1 Повторные поступления и остаток

Каждый уникальный подтверждённый входящий перевод является отдельным триггером, но повторная доставка одного и того же log event не создаёт второе списание. Если поступило несколько переводов, пока предыдущая операция ожидает подтверждения, события сохраняются и обрабатываются по очереди с повторным чтением баланса перед каждой операцией.

При балансе ровно 10 USDT сумма списания составит 9.8 USDT. Остаток после списания ниже порога, поэтому новых списаний не будет до следующего входящего события, которое снова удовлетворит порогу. Периодического списания без новых поступлений в этом варианте нет.

98% рассчитываются заново от текущего баланса при каждом подходящем поступлении. Поэтому несколько поступлений могут привести к нескольким отдельным переводам; суммарно за время работы может быть списано больше 98% первоначального баланса. Это накопительное поведение должно быть явно показано в согласии пользователя.

Примеры без срабатывания аварийных ограничителей: при балансе 100 USDT расчётная сумма — 98 USDT; при балансе 1,000 USDT — 980 USDT. Фиксированного верхнего предела на эти суммы в ТЗ нет.

## 6. Разовое списание администратором

- Разовое списание задаётся в USDT с шестью десятичными знаками; преобразование в base units — строго десятичное, без округления вверх.
- Перед транзакцией администратор указывает причину. Бот показывает предпросмотр и требует отдельного повторного подтверждения; повторное нажатие, просроченный callback или изменённый payload не выполняют списание.
- При подтверждении заново читаются on-chain баланс и allowance; проверяются пользователь, активная связь, адрес получателя, лимит одной операции, дневной лимит и общий аварийный лимит.
- Нельзя вводить произвольный адрес получателя в команде. Получатель берётся только из серверной конфигурации/allowlist.
- On-chain approval не должно трактоваться как право администратора на любое списание без предусмотренного пользовательскими условиями основания. Отдельная кнопка администратора не заменяет такое основание.
- Разовые операции и автосписания используют общий учёт лимитов и общий журнал, чтобы нельзя было обойти дневной лимит через параллельные кошельки или разные интерфейсы.

## 7. Блокчейн и финансовая надёжность

- Первый релиз: только `chain_id = 1`, официальный Ethereum Mainnet USDT и канонический Uniswap Permit2 `AllowanceTransfer`.
- В проекте `transferFrom` вызывается у Permit2 с параметрами owner, recipient, amount и token. Прямой `USDT.transferFrom` и EIP-2612 для выбранного USDT не используются.
- Операторский private key остаётся только в серверном secret storage. Он не отправляется в Telegram, браузер, клиент Mini App, URL, логи или ответы API.
- Разрешение из БД является только индексом/историей. Перед каждой отправкой требуется свежая проверка разрешений в Ethereum.
- Отключение MetaMask/WalletConnect-сессии само по себе не отзывает on-chain approval; UI и бот должны различать отключённую транспортную сессию, отозванное согласие на автосписание и отозванное on-chain разрешение.
- RPC-ошибки, недостаточный gas оператора, тайм-ауты и низкая ликвидность оператора приводят к остановке/повторной проверке, а не к обходу лимитов. Пользовательские USDT не используются для gas.
- Сканер поддерживает повторное сканирование блоков, reorg/replay protection и уникальность event ID. Уровень подтверждения задаётся конфигурацией, не ниже согласованного production-порога; при доступности используется finalized block.
- Функции списания по умолчанию выключены. Отдельные флаги для manual и auto path; авто-путь нельзя включить простым развёртыванием кода.

## 8. Роли, авторизация и аудит

- Новый bot token и webhook secret хранятся только в Replit Secrets как отдельные секреты. Существующий `TELEGRAM_BOT_TOKEN` не переиспользуется без проверки владельца и webhook-конфигурации.
- Для каждого webhook update проверяются Telegram secret token, идентификатор отправителя, тип чата и allowlist `ADMIN_TELEGRAM_IDS`. Username, имя профиля и номер телефона не являются идентификаторами авторизации.
- Все команды, в том числе чтение данных, доступны только allowlisted администраторам. Неавторизованному отправителю бот отвечает нейтрально и не подтверждает наличие пользователя/кошелька.
- Для финансового действия записываются admin Telegram ID, target Telegram ID/wallet, действие, причина, amount base units, recipient, charge ID, idempotency key, результат и tx hash. Секреты, ключи, Telegram initData и полный payload webhook не логируются.
- В боте нет команд удаления пользователя, удаления разрешения или очистки финансовой истории. Удаление должно быть мягким/анонимизирующим по утверждённой политике хранения; финансовый аудит нельзя терять каскадным удалением.
- Изменение адреса назначения, лимитов и аварийного состояния требует отдельного контролируемого процесса. Уведомления об изменении параметров направляются всем администраторам.

### 9.2 Миграция есть в репозитории, но live API не видит таблицы

В `supabase/migrations/005_internal_evm_authorizations.sql` определены следующие таблицы:

- `internal_evm_authorizations`: `id`, `telegram_id`, `owner_address`, `chain_id`, `token_address`, `permit2_operator_address`, `token_allowance`, `permit2_allowance_amount`, `permit2_expiration`, `permit2_nonce`, `approval_tx_hash`, `permit_tx_hash`, `status`, `verified_at`, `created_at`, `updated_at`; уникальность `owner_address`.
- `internal_evm_authorization_challenges`: `id`, `telegram_id`, `owner_address`, `nonce`, `expires_at`, `used_at`, `created_at`.
- `internal_evm_charges`: `id`, `telegram_id`, `authorization_id`, `idempotency_key`, `recipient_address`, `amount_base_units`, `status`, `tx_hash`, `error_message`, `created_at`, `updated_at`; уникальный `idempotency_key`.

Прямые read-only запросы к Supabase REST по всем трём таблицам вернули HTTP 404 `PGRST205` (“Could not find the table ... in the schema cache”). Поэтому нельзя утверждать, что эти таблицы сейчас доступны работающему серверу. Возможные причины: миграция не применена, таблицы созданы не в exposed schema либо PostgREST schema cache не обновлён. **До реализации нужно подтвердить таблицы в каталоге PostgreSQL/Supabase SQL Editor и обеспечить их доступность service-role backend через REST/RPC.** Ничего в БД в рамках этого ТЗ не менялось.

### 9.3 Что уже реализовано в серверном коде

- Есть HTTP endpoint ручного EVM списания `/api/admin/evm/charges`, доступный через авторизованную сессию и `ADMIN_TELEGRAM_IDS`.
- Списание использует Permit2, проверяет активную запись разрешения, свежую on-chain allowance, allowlist получателя, idempotency key и дневные/разовые лимиты из конфигурации.
- Ручной путь fail-closed: код требует `EVM_MANUAL_CHARGE_ENABLED=1`, лимит операции, дневной лимит и allowlist. Значения enable/cap-переменных не найдены в `.replit` или `.env.example`; включённость в runtime отдельно не подтверждалась.
- Есть Mini App интерфейс reward admin. Обработчиков Telegram Bot API команд или отдельного админ-бота в исходниках не найдено.

### 9.4 Полей/сущностей, которых не хватает для автосписания

Имеющиеся таблицы не хранят отдельное пользовательское согласие, триггер входящего поступления и связь события с автоматической операцией. Для реализации нужны:

1. **`internal_evm_autodebit_consents`** — согласие на конкретный кошелёк: `id`, `telegram_id`, `authorization_id`, `owner_address`, `policy_version`, hash/идентификатор принятого текста, `enabled`, фиксированное `percentage_bps = 9800`, `minimum_balance_base_units = 10000000`, trigger type, `accepted_at`, `revoked_at`, `created_at`, `updated_at`. Ограничение: не более одного включённого согласия на кошелёк.
2. **`internal_evm_usdt_incoming_events`** — события входящих USDT: `chain_id`, `token_address`, `tx_hash`, `log_index`, `block_number`, `block_hash`, `from_address`, `to_address`, `amount_base_units`, confirmation/status, timestamps. Уникальный ключ `(chain_id, tx_hash, log_index)` для идемпотентности.
3. **`internal_evm_scan_state`** — устойчивый курсор сканирования Ethereum по сети/контракту, последний обработанный finalized block и hash. Нужен для возобновления после перезапуска и обработки reorg.
4. **Расширение `internal_evm_charges`** — как минимум `charge_type` (`manual`/`auto_deposit`), `consent_id`, `trigger_event_id`, balance snapshot, `requested_by_admin_telegram_id` и reason для ручного списания, attempt count, `submitted_at`, `confirmed_at`, `last_error_code`. `trigger_event_id` должен быть уникален для auto-charge. Статусы должны различать зарезервированную, отправленную/ожидающую, подтверждённую, окончательно неуспешную и требующую reconciliation операцию.
5. **`internal_admin_bot_audit_log`** — actor ID, команда/действие, target user/wallet, correlation/charge ID, результат и timestamp без секретов и лишних персональных данных.
6. Для списка одобрений нужны свежесть проверки и последний on-chain результат, например `last_onchain_checked_at` и `last_onchain_status` либо отдельная таблица проверок. `verified_at` фиксирует момент первоначальной проверки и не заменяет текущую проверку.

Любые новые таблицы/RPC должны иметь включённый RLS, закрытый доступ для `anon`/`authenticated` и минимально необходимые права `service_role`. Резервирование списания, idempotency и проверка лимитов должны быть атомарными. Текущая блокировка записи одной authorization может не сериализовать операции разных кошельков одного Telegram-пользователя; лимиты пользователя нужно защищать общей DB-блокировкой/эквивалентным механизмом.

## 10. Состояния и обработка ошибок

Для входящего события: `observed → confirmed → queued → processed`, либо `ignored_below_threshold`, `waiting_for_consent`, `reorged`.

Для списания: `reserved → submitted → confirming → confirmed`; при неизвестном результате — `reconciliation_required`; при достоверном отказе — `failed`; до отправки возможен `cancelled`. Переходы фиксируются только сервером/RPC, не командой из чата.

Критические случаи:

- consent выключен/отозван — auto job не создаётся;
- разрешение истекло, отозвано или уменьшилось — fail closed, уведомить о необходимости повторной привязки/approval; новую подпись не запрашивать автоматически;
- баланс уже изменился — пересчитать до отправки или остановить;
- RPC недоступен — не менять запись на «успешно» и не отправлять обходным путём;
- недостаточно gas у оператора — очередь остаётся остановленной/ожидающей, не использовать gas пользователя;
- дубликат события/callback — вернуть текущую операцию по idempotency key, не создавать новую;
- транзакция могла попасть в сеть, но receipt не получен — reconciliation до любой повторной отправки;
- дневной/операционный/глобальный лимит превышен — блокировать операцию, уведомить администратора;
- злоупотребление админ-командами или повторные ошибки — rate limit, временная блокировка, security alert.

## 11. Конфигурация и выключатели

Предлагаемые имена конфигурации (значения задаются позже через безопасные настройки, не в коде и не в документе):

- `ADMIN_BOT_TOKEN` — секрет отдельного бота;
- `ADMIN_BOT_WEBHOOK_SECRET` — секрет проверки webhook;
- `ADMIN_TELEGRAM_IDS` — allowlist администраторов;
- `EVM_AUTO_CHARGE_ENABLED` — отдельный флаг auto path, по умолчанию `0`;
- `EVM_AUTO_CHARGE_RECIPIENT` — фиксированный адрес назначения; обязателен и должен входить в `EVM_CHARGE_RECIPIENT_ALLOWLIST`;
- `EVM_AUTO_CHARGE_MIN_BALANCE_BASE_UNITS` — порог, для текущей политики `10000000`;
- `EVM_AUTO_CHARGE_PERCENT_BPS` — фиксированная политика `9800`;
- числовые значения дневного лимита на кошелёк и глобального аварийного лимита должны быть утверждены до включения. Отдельный фиксированный максимум одной auto-транзакции не задан; если аварийный лимит превышен, транзакция блокируется целиком, а не уменьшается;
- RPC, operator key и существующий recipient allowlist остаются только в server-side secrets.

Если обязательная настройка отсутствует/невалидна, автосписание выключено. Изменение allowlist, operator wallet или лимитов требует проверяемого deployment/config процесса и записи в аудит.

## 12. Нефункциональные требования и критерии приёмки

### Безопасность

- Ни один пользователь без отдельного согласия не списывается автоматически.
- Ни один Telegram ID или wallet address не может быть изменён командой на произвольную цель без серверной проверки существующей связи.
- Ни одна транзакция не отправляется на адрес вне allowlist.
- Один blockchain event не приводит более чем к одному auto charge, даже после рестарта/повторной доставки.
- Повторное нажатие «подтвердить» не создаёт дополнительную ручную транзакцию.
- Невалидная/недоступная БД, RPC или конфигурация приводит к отказу по умолчанию.
- Баланс внутреннего ledger не участвует в on-chain переводах и не выдаётся за on-chain данные.

### Данные и корректность

- `/stats` различает число зарегистрированных пользователей, пользователей с записью разрешения, активные on-chain-разрешения и активные автосогласия.
- `/approved` не называет DB-статус доказательством текущей on-chain активности.
- `/balance` показывает точное время/блок чтения и разделяет on-chain USDT и внутренний USDT.
- 98% вычисляется через целочисленную арифметику; порог 10 USDT проверяется до расчёта и сумма не превышает актуальный balance/allowance.
- Списания, попытки, статусы, tx hashes и причины доступны в журнале; ошибочный или неизвестный результат не скрывается.
- Лимиты атомарны и не обходятся одновременными списаниями с нескольких кошельков одного Telegram-пользователя.

### Проверки перед запуском

1. Подтвердить через SQL-каталог реальную схему Supabase; применить/исправить EVM-миграцию и добиться доступности таблиц через backend API.
2. Проверить все ограничения, индексы, foreign keys, RLS и права service role.
3. Проверить unit/integration сценарии: подтверждённое поступление, порог `9.999999/10.000000 USDT`, отсутствие согласия, отзыв согласия, истёкшее/отозванное разрешение, дубликат log, reorg, низкий gas, RPC timeout, неизвестный tx outcome, дневной лимит, два параллельных кошелька, два администратора и повторное подтверждение.
4. Прогнать scanner в dry-run без подписи и переводов; сопоставить найденные events и рассчитанные суммы с блокчейн-данными.
5. Включать production transfer path только отдельным согласованным шагом после пользовательского UI согласия, проверки recipient, лимитов, мониторинга и успешного тест-плана.

## 13. Блокеры перед реализацией

1. **Блокер БД:** три EVM-таблицы из migration 005 не видны через текущую Supabase REST schema cache (`PGRST205`). Пока это не исправлено и не подтверждено чтением каталога/REST API, нельзя полагаться на записи approvals и charges.
2. **Recipient:** фактический адрес назначения должен быть выбран и серверно ограничен allowlist. В ТЗ и переписке никаких secret/env значений не раскрывается.
3. **Согласие:** требуется согласовать текст политики автосписания, retention/audit и процесс отзыва до включения любых переводов.
4. **Telegram webhook:** для отдельного бота нужны новый bot token и webhook secret; перед установкой webhook проверить, что этот токен не используется другим сервисом.
5. **Production caps:** задать дневной лимит на кошелёк, глобальный аварийный лимит и аварийную остановку до включения auto path. Фиксированный максимум суммы одной auto-транзакции не задан; добавлять его можно только как отдельное согласованное продуктовое ограничение.
